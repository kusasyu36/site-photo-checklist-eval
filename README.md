# site-photo-checklist-eval

工事現場の写真を点検チェックリスト12項目に照らして Vision-Language Model（VLM）に判定させ、
人手のラベルと突き合わせて、どの項目をどう間違えるかを数える評価ハーネスです。

正解率だけでなく、見落とし・誤検出・不明のどれが多いか、どの項目に偏るかを出します。
プロンプトに現場側の確認観点を足すと何が変わるかを、同じ写真で比べます。

```
写真 + チェックリスト ──► VLM（Claude、Read ツールのみ許可） ──► JSON（項目ごとに yes/no/unclear + 根拠）
                                                                 │
   人手ラベル（1/0/?） ◄──── 採点（P/R/F1・全項目一致・不明回数） ◄──┘
                                    │
                          失敗の型（miss / false_alarm / abstain / format_invalid / llm_error）× 項目
```

## 結果

claude-sonnet-5、写真20枚、3条件、各1試行、合わせて60回の呼び出し。
採点対象は 204 セル。20枚 × 12項目から、作者が判定できず "?" にした 36 セルを除いた数です。

| 条件 | プロンプト | precision | recall | F1 | accuracy | 全項目一致率 | 不明 | 見落とし | 誤検出 | 形式不正 |
|---|---|---|---|---|---|---|---|---|---|---|
| bare | 定義のみ | 0.93 | 0.95 | 0.94 | 0.96 | 13/20 | 23 | 1 | 5 | 0 |
| hinted | 定義と確認観点 | 0.92 | 0.93 | 0.93 | 0.95 | 12/20 | 25 | 1 | 6 | 0 |
| framed | 定義と、写っていなければ いいえ とする規則 | 0.91 | 0.93 | 0.92 | 0.94 | 12/20 | 16 | 4 | 7 | 0 |

不明は no として採点しているので、不明が多いほど recall と一致率が下がります。
形式不正と呼び出し失敗は60回のうち0回でした。検証コードは発動しませんでしたが、発動する経路はテストで確かめてあります。

### 読み取り

詳しい数字は [results/summary.md](results/summary.md)、失敗ごとの根拠は [data/LABEL_AUDIT.md](data/LABEL_AUDIT.md) にあります。

1. 失敗の大半は誤りではなく、不明と答えて判断を避けたものでした。bare では 204 セル中 23 が不明で、見落としは 1、誤検出は 5 です。
   不明の根拠を読むと、p10 や p17 で「画角の外に仮囲いがある可能性があるので判断できない」と書いています。
   VLM は現場に存在するかを聞かれたと解釈し、作者のラベルは写真に写っているかで付けていました。
   これはモデルの問題ではなく、チェックリストの設問がどちらなのかを決めていなかったことによります。
2. 規則を明示すると不明は減りますが、誤りに変わります。framed で不明は 23 から 16 に減り、見落としは 1 から 4、誤検出は 5 から 7 に増えました。
   不明は人の確認に回せますが、誤りは回せません。不明を減らすこと自体を目標にすると見落としが増えます。
   運用では、不明を残して人に回す設計と、誤りを減らす設計を分けて考える必要があります。
3. 確認観点を足した hinted は効きませんでした。不明はむしろ 23 から 25 に増え、ヘルメット未着用で誤検出が出ました。
   観点に、判断できないときは不明にすると書いたので、そのとおり慎重になった、とも読めます。
   観点は作者が書いたものです。現場の判断基準を本当に言語化できているかを先に確かめないと、足しても効きません。
4. 項目ごとの偏りがはっきりあります。足場、公道、水、架空線はほぼ全問正解でした。
   苦手なのは、隣接構造物、資材の仮置き、仮囲い、掘削です。工事対象と既存物の区別、廃材コンテナを含むか、設置済みか置いてあるだけか、土の山と掘り込みの区別、というように、どれも定義の境界が曖昧な項目です。
   VLM の答えを読んで初めて、作者のラベルが自分の定義と矛盾している箇所が見つかりました。p15 と p14 の掘削がそれです。
5. 解像度の限界があります。遠景の人物が作業員か通行人か、小さく写る掘削機、電線は、全条件で不明か見落としでした。
   写真全体を1枚渡すだけでは拾えないので、切り出しや物体検出の前処理が候補になります。

このサイズの評価でも、モデルの精度より先に、設問の定義と正解ラベルの一貫性の問題が表に出ました。
専門家の判断基準を項目に落とす作業を、モデルの検証より先にやる根拠になります。

## 何を測っているか

### 題材

写真は Wikimedia Commons の CC ライセンス写真20枚です。足場、クレーン、掘削、仮囲い、道路工事、解体などが写っています。
リポジトリには含めず、`scripts/download_images.py` で取得します。出典は [data/CREDITS.md](data/CREDITS.md) にあります。

チェックリストは12項目で、[src/spce/checklist.py](src/spce/checklist.py) に定義があります。
足場、建設機械、作業員、ヘルメット未着用の作業員、仮囲いとバリケード、掘削と土留め、資材の仮置き、
隣接する既存構造物、公道と交通、看板と標識、水と泥、架空線です。

正解ラベルは、建設の専門家ではない作者が写真を見て 1 / 0 / "?" を付けました。
"?" は作者にも判断できなかった項目で、採点から外します。240 セル中 36 が "?" でした。

### 3つの条件

| 条件 | プロンプトに入れるもの | 何を模しているか |
|---|---|---|
| bare | 項目名と定義だけ | チェックリストをそのまま渡した状態 |
| hinted | 定義に加えて、各項目の確認観点。何を見て判断するか、迷ったら不明にする基準 | 現場の判断基準を言語化して渡した状態 |
| framed | 定義に加えて、写真に写っていなければ いいえ、範囲外の可能性は考えない、という判定規則 | 設問の曖昧さを潰した状態。bare の結果を見て追加した |

確認観点は作者が書いたもので、本物の現場のノウハウではありません。
この差分が測っているのは、判断基準を文章で足したときに VLM の答えがどの項目でどの向きに動くかであって、観点の正しさではありません。

### 指標

項目ごとの precision / recall / F1 を出します。unclear は答えなかったものとして no 扱いで採点し、別に不明の回数を数えます。
写真ごとに、採点対象の項目が全部合っていたかを全項目一致率として出します。

失敗の型は5つです。miss は見落とし、false_alarm は誤検出、abstain_on_clear は作者が判定できた項目で不明と答えたもの、
format_invalid は JSON 崩れや項目欠け、llm_error は呼び出し失敗です。型ごとに、どの項目で多いかを出します。

### ハーネス側の設計

VLM の出力は信用しません。JSON の取り出し、全項目の存在、値が3値のいずれかであることを検証し、
不正なら format_invalid として記録します。コードは [src/spce/schema.py](src/spce/schema.py) です。

VLM の呼び出しは `claude -p` の子プロセスです。画像を開くための Read ツールだけを許可し、シェル、書き込み、Web は使わせません。
タイムアウトと再試行があります。コードは [src/spce/vlm.py](src/spce/vlm.py) です。

結果は1枚ごとに JSONL に追記します。途中で落ちても済んだ分は残り、再実行は未処理の写真だけ回します。
集計は VLM を使わずコードで行います。テスト17本は Mock バックエンドで動き、ネットワークも API も要りません。

## 使い方

```bash
uv venv --python 3.12 .venv && uv pip install --python .venv/bin/python -e ".[dev]"
.venv/bin/python -m pytest -q                      # 17 passed
.venv/bin/python scripts/download_images.py        # 画像20枚を取得

# VLM で評価（claude CLI が必要。Read ツールのみ許可して実行される）
.venv/bin/python -m spce.run_eval --condition bare   --trial 1
.venv/bin/python -m spce.run_eval --condition hinted --trial 1
.venv/bin/python -m spce.run_eval --condition framed --trial 1
.venv/bin/python -m spce.report results/pred_*_t1.jsonl
```

`--backend mock` でオフラインの決定的バックエンド、`MOCK_INVALID=1` で不正出力の経路を試せます。

## この検証の限界

- ラベルは専門家ではない1人の判断です。"?" を外しているので、難しい項目ほど採点から抜けています。専門家が同じ写真をラベルすれば、正解自体が動く項目があります。隣接構造物、掘削、資材がそうです。
- 各条件1試行です。VLM の出力は同じ入力でも揺れるので、条件間の差は試行を重ねないと確定しません。`--trial 2` 以降を回して同じ集計にかけられます。
- framed 条件は bare の結果を見てから追加しました。事後に足した条件なので、その差は仮説の確認であって独立な検証ではありません。
- ラベル監査で見つかった作者側の誤り、p15 と p14 の掘削などは、v1 のまま直していません。評価を見てからラベルを直すと採点が甘くなるためです。論点は [data/LABEL_AUDIT.md](data/LABEL_AUDIT.md) に残し、v2 で扱います。
- 写真は Commons の 1280px 縮小版です。ヘルメットや架空線のような小さい対象は解像度の影響を受けます。
- 確認観点は作者が書いたもので、現場の実際の判断基準とは違います。
- 20枚、12項目の小さな評価です。傾向を見るためのもので、モデルの優劣を決めるものではありません。

## 構成

```
src/spce/
  checklist.py   12項目の定義と確認観点
  prompts.py     bare / hinted / framed のプロンプト構築
  vlm.py         claude -p バックエンド（Read のみ許可）と Mock
  schema.py      出力の検証（InvalidOutput）
  run_eval.py    実行 CLI（追記型 JSONL）
  metrics.py     採点（P/R/F1・全項目一致・不明）
  failures.py    失敗の型の分類
  report.py      条件別の集計と Markdown / JSON 出力
data/
  manifest.jsonl 画像の URL・ライセンス・作者
  labels.jsonl   正解ラベル（1 / 0 / "?"）v1 凍結
  LABEL_AUDIT.md 評価後に見つかったラベル・定義の論点
  CREDITS.md     出典一覧
results/
  pred_*.jsonl   VLM の生出力（根拠と要確認ポイントを含む）
  summary.md / summary.json
tests/           17本（Mock で完結）
```
