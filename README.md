# site-photo-checklist-eval

工事現場の写真を点検チェックリスト12項目で確認する、小さな評価実験です。
画像を読める LLM に写真と項目を渡し、項目ごとに yes / no / unclear と根拠を返させ、
作者が付けた参照ラベルと同じ条件で採点して、どの項目をどう間違えるかを数えます。

## 何を入力し、何を出力するか

```
写真＋チェックリスト ──► Claude（画像入力対応 LLM。Read ツールのみ許可） ──► JSON（項目ごとに yes / no / unclear と根拠）
                                                                   │
   参照ラベル（1 / 0 / ?） ◄──── 採点（P/R/F1、全項目一致、unclear の回数） ◄──┘
                                    │
                          失敗の型（miss / false_alarm / abstain / format_invalid / llm_error）× 項目
```

- 入力: Wikimedia Commons の CC ライセンス写真20枚と、12項目の定義文
- 出力: 項目ごとの yes / no / unclear、その根拠1文、現地で確認すべき点の候補（notable_points、最大5件）
- 採点: 参照ラベルと突き合わせて、precision / recall / F1、全項目一致率、unclear の回数、失敗の型を出す

## Claude の位置づけ

この README で VLM と書くのは、画像を見て文章で判定する役割の名前です。本実験ではその役割を Claude に担当させました。
Claude は Anthropic のモデルで、画像入力に対応した LLM です。CLIP のように画像と文章の近さを数字で返すモデルとは役割が違います。
以下では、モデルのことは Claude またはモデルと書きます。

## 何を比べたか

| 条件 | プロンプトに入れるもの |
|---|---|
| bare | 項目名と定義だけ |
| hinted | 定義に加えて、作者が作成した仮の確認観点。何を見て判断するか、迷ったら unclear にする基準 |
| framed | 定義に加えて、写真に写っていなければ no、範囲外の可能性は考えない、という判定規則。bare の結果を見てから追加した |

確認観点は作者が書いたもので、建設の専門家が確認したものではありません。
bare と hinted の差が測るのは、確認観点を文章で足すと出力がどう変わるかであって、観点の正しさではありません。

## 結果

claude-sonnet-5、写真20枚、3条件、各1試行、合わせて60回の呼び出し。
採点対象は 204 セル。20枚 × 12項目から、作者が判定できず "?" にした 36 セルを除いた数です。

| 条件 | precision | recall | F1 | accuracy | 全項目一致率 | unclear | 見落とし | 誤検出 | 形式不正 |
|---|---|---|---|---|---|---|---|---|---|
| bare | 0.93 | 0.95 | 0.94 | 0.96 | 13/20 | 23 | 1 | 5 | 0 |
| hinted | 0.92 | 0.93 | 0.93 | 0.95 | 12/20 | 25 | 1 | 6 | 0 |
| framed | 0.91 | 0.93 | 0.92 | 0.94 | 12/20 | 16 | 4 | 7 | 0 |

unclear は no として採点しているので、unclear が多いほど recall と一致率が下がります。
形式不正と呼び出し失敗は60回のうち0回でした。検証コードは発動しませんでしたが、発動する経路はテストで確かめてあります。

この数字から、専門家と比べたモデルの性能や、現場での安全確認に使えるかどうかは判断できません。
参照ラベルは建設の専門家ではない作者1名が付けたもので、写真は20枚、試行は各条件1回です。

## 結果から言えること

詳しい数字は [results/summary.md](results/summary.md)、失敗ごとの根拠は [data/LABEL_AUDIT.md](data/LABEL_AUDIT.md) にあります。

1. 今回のデータでは、誤った yes / no より unclear のほうが多かった。bare では 204 セル中 23 セルが unclear、見落としは 1 セル、誤検出は 5 セルでした。
   p10 と p17 では、モデルが画角の外に仮囲いがある可能性を理由に unclear を返しました。一方、参照ラベルは写真に写っているかで付けていました。
   この違いが unclear の一因と考えられます。チェックリストの設問が、写真に写っているかなのか、現場に存在するかなのかを決めていませんでした。
2. unclear を減らす規則を加えた framed では、unclear は 23 から 16 に減った一方、見落としは 1 から 4、誤検出は 5 から 7 に増えました。
   unclear の削減だけを目標にすると、別の誤りが増える可能性があります。
   実運用に使うなら、モデルの判定を最終確認とせず、unclear だけでなく重要な yes / no も人が確認する設計が必要です。
3. hinted では unclear が 23 から 25 に増え、ヘルメット未着用で誤検出が出ました。確認観点に、判断できないときは不明にすると明記したので、今回の結果はその指示に沿った可能性があります。
   ただし1試行なので、確認観点そのものが原因だとは確定できません。
4. 項目ごとの偏りがあります。足場、公道、水、架空線はほぼ全問正解でした。
   不一致が多いのは、隣接構造物、資材の仮置き、仮囲い、掘削です。工事対象と既存物の区別、廃材コンテナを含むか、設置済みか置いてあるだけか、土の山と掘り込みの区別が、定義に書かれていませんでした。
5. p14 と p15 の掘削では、定義と参照ラベルの組み合わせに不整合が見つかりました。モデルの答えを読んで初めて気づいたものです。
   このため、今回の結果をモデルの優劣だけで解釈することはできません。
6. 遠景の人物が作業員か通行人か、小さく写る掘削機、電線は、全条件で unclear か見落としでした。写真全体を1枚渡すだけでは拾えないので、切り出しや物体検出の前処理が候補になります。

次回は、モデルを評価する前に、各項目について、写っていれば yes なのか、現場に存在すると推測できれば yes なのかを固定し、複数人で参照ラベルを確認します。

## 結果から言えないこと

- 専門家と比べたときのモデルの性能。参照ラベルが専門家のものではないため
- 現場の安全確認や法令適合に使えるかどうか。notable_points は探索的な参考出力で、精度と再現性の採点対象ではなく、現地の安全判断や法令適合性を保証しません
- 他の写真、他の項目、他のモデルへの一般化。20枚、12項目、1モデル、各1試行のため
- 条件間の差の大きさ。同じ入力でも出力は揺れるので、試行を重ねないと確定しません

## 参照ラベルと限界

- 参照ラベルは、建設の専門家ではない作者1名が写真を見て 1 / 0 / "?" を付けたものです。"?" は作者にも判断できなかった項目で、採点から外します。240 セル中 36 が "?" でした。"?" を外しているので、難しい項目ほど採点から抜けています
- 各条件1試行です。`--trial 2` 以降を回して同じ集計にかけられます
- framed 条件は bare の結果を見てから追加しました。その差は仮説の確認であって、独立な検証ではありません
- ラベル監査で見つかった不整合、p14 と p15 の掘削などは、v1 のまま直していません。評価を見てからラベルを直すと採点が甘くなるためです。論点は [data/LABEL_AUDIT.md](data/LABEL_AUDIT.md) に残し、v2 で扱います
- 写真は Commons の 1280px 縮小版です。ヘルメットや架空線のような小さい対象は解像度の影響を受けます
- 12項目の定義文と確認観点は、評価に使ったものをそのまま [src/spce/checklist.py](src/spce/checklist.py) に残しています。文面に括弧や例外が混ざっていますが、結果の再現性のため変更していません

## 指標と失敗の型

項目ごとの precision / recall / F1 を出します。unclear は答えなかったものとして no 扱いで採点し、別に unclear の回数を数えます。
写真ごとに、採点対象の項目が全部合っていたかを全項目一致率として出します。

失敗の型は5つです。miss は見落とし、false_alarm は誤検出、abstain_on_clear は作者が判定できた項目で unclear と答えたもの、
format_invalid は JSON 崩れや項目欠け、llm_error は呼び出し失敗です。型ごとに、どの項目で多いかを出します。

## ハーネス側の設計

モデル出力はそのまま採点せず、JSON として読めるか、12項目が全部あるか、値が3値のいずれかを検証します。
不正なら format_invalid として記録します。コードは [src/spce/schema.py](src/spce/schema.py) です。

呼び出しは `claude -p` の子プロセスです。画像を開くための Read ツールだけを許可し、シェル、書き込み、Web は使わせません。
タイムアウトと再試行があります。コードは [src/spce/vlm.py](src/spce/vlm.py) です。

結果は1枚ごとに JSONL に追記します。途中で落ちても済んだ分は残り、再実行は未処理の写真だけ回します。
集計はモデルを使わずコードで行います。テスト18本は Mock バックエンドで動き、ネットワークも API も要りません。

## 実行方法

```bash
uv venv --python 3.12 .venv && uv pip install --python .venv/bin/python -e ".[dev]"
.venv/bin/python -m pytest -q                      # 18 passed
.venv/bin/python scripts/download_images.py        # 画像20枚を取得

# 評価（claude CLI が必要。Read ツールのみ許可して実行される）
.venv/bin/python -m spce.run_eval --condition bare   --trial 1
.venv/bin/python -m spce.run_eval --condition hinted --trial 1
.venv/bin/python -m spce.run_eval --condition framed --trial 1
.venv/bin/python -m spce.report results/pred_*_t1.jsonl
```

`--backend mock` でオフラインの決定的バックエンド、`MOCK_INVALID=1` で不正出力の経路を試せます。

## ファイル構成

```
src/spce/
  checklist.py   12項目の定義と確認観点（評価に使った文面のまま）
  prompts.py     bare / hinted / framed のプロンプト構築
  vlm.py         claude -p バックエンド（Read のみ許可）と Mock
  schema.py      出力の検証（InvalidOutput）
  run_eval.py    実行 CLI（追記型 JSONL）
  metrics.py     採点（P/R/F1、全項目一致、unclear）
  failures.py    失敗の型の分類
  report.py      条件別の集計と Markdown / JSON 出力
data/
  manifest.jsonl 画像の URL、ライセンス、作者
  labels.jsonl   参照ラベル（1 / 0 / "?"）v1 凍結
  LABEL_AUDIT.md 評価後に見つかった参照ラベルと定義の論点
  CREDITS.md     出典一覧
results/
  pred_*.jsonl   モデルの生出力（根拠と notable_points を含む）
  summary.md / summary.json
tests/           18本（Mock で完結）
```
